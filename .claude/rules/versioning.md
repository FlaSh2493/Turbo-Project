# 버전 등급 규칙

배포되는 패키지는 **`@turbo-project/afds`** 하나다. `packages/afds-registry` 는 `private: true` 라 npm 에 나가지 않고, 컴포지션은 `registry.json` 으로 배포된다.

**머지하면 즉시 자동 배포된다** — `release.yml` 이 `main` push 로 돌아 범프·publish 를 한다. 사람이 개입하는 지점이 없고 등급을 검사하는 기계도 없다.

## ★ major 는 사용자 승인 없이 올리지 않는다

**`major` 를 쓰려면 `AskUserQuestion` 으로 사용자에게 물어 승인받는다.** 리뷰가 「등급이 맞다」고 해도 그것으로 갈음하지 않는다.

**되돌리는 비용이 비싸서다.** 실측: `2.0.0` 하나를 되돌리는 데 되돌리기 PR · 레지스트리 삭제 **2회**(중간에 재배포됐다) · git 태그와 GitHub Release 삭제가 들었고, 그동안 잘못된 버전이 `latest` 로 노출됐다.

**물을 수 없으면 `major` 를 쓰지 말고 멈춘다.** 비대화형·자율 실행에서는 답을 받을 수 없다. 「물었는데 답이 없으니 진행」은 승인이 아니다.

물을 때 함께 제시할 것 — **무엇이 깨지는가** · **왜 minor 로 안 되는가** · **알려진 소비처가 받는지**.

## 등급

| 등급         | 무엇                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| **major**    | 컴포넌트·훅·`lib` 의 제거나 시그니처 변경 · `exports` 키 제거 · peer 요구 상향 |
| **minor**    | 추가 · 동작을 보존하는 리팩터 · 별도 채널이 나르는 계약 변경                   |
| **patch**    | 배포 산출물의 버그 수정                                                        |
| **무릴리스** | 배포 산출물이 바뀌지 않는 변경 — **빈 changeset**(`---` 두 줄)을 쓴다          |

**대부분이 무릴리스다** — 실측: 최근 60커밋의 changeset 34건 중 **31건이 빈 것**이다. 문서·테스트·CI·규칙 변경에 `patch` 를 달면 **읽을 것이 없는 릴리스가 나간다.**

**판정 기준은 「배포 산출물의 동작이 바뀌는가」다** — 「그 파일이 배포되는가」가 아니다. `packages/afds` 의 `files` 가 `dist`·`tokens`·`src` 이므로 `src` 아래의 `__test__` 디렉터리도 배포된다(69파일). 그래도 테스트·주석 변경은 산출물의 동작을 바꾸지 않으므로 무릴리스다. 배포 밖인 것은 `scripts/` · `.claude/` · `.github/` · 루트 설정이다.

**빈 changeset 은 「패키지 파일을 만졌을 때」 쓴다.** `.github/`·루트만 만진 PR 은 `check-changeset.sh` 가 changeset 을 요구하지 않으므로 **쓸 자리가 없다** — 그때는 없는 것이 맞다.

## 별도 계약 채널이 있으면 그것으로 나른다

`manifest.json` 은 **자기 버전을 싣는다** — `schemaVersion`. 그 스키마만 바뀌었으면 **그 값을 올리고 패키지 major 를 함께 쓰지 않는다.**

- `schemaVersion` — 필드 추가는 minor · 제거나 의미 변경은 major

`registry.json` 은 다르다 — **shadcn 규격을 따를 뿐 자기 계약 버전이 없다**(`$schema` 가 외부 스키마를 가리킨다). 규격이 계약이므로 우리가 올릴 값이 없다.

**이유는 신호 대역이다.** 패키지 major 는 **모든 소비처**에게 「업그레이드 전에 검토하라」를 방송한다. 코드 표면이 그대로인데 그것을 쓰면, 다음에 **진짜 컴포넌트 API 를 깰 때** 소비처가 번호만으로 두 경우를 구분할 수 없다.

**대가를 크게 보라** — 이 채널로 나른 신호는 그 스키마를 읽는 소비처에만 닿고, 실측으로 `schemaVersion` 을 읽고 분기하는 소비처는 **현재 0** 이다. 패키지 major 보다 나은 이유는 **거짓 신호를 보내지 않는 것**이고, 실제 전달 경로는 changeset 본문이다.

## 값이 낮은 파괴적 변경은 모은다

죽은 필드 하나를 지우려고 major 를 쓰지 마라. **「다음 major 에서 제거」로 표시하고** 진짜 파괴적 변경과 함께 낸다.

## 배포된 버전을 지울 때 — `main` 이 그것을 선언하고 있으면 되살아난다

`release.yml` 의 범프는 조건부지만 **publish 는 조건 없이 매 `main` push 에서 돈다.** `changeset publish` 는 로컬 버전이 레지스트리에 없으면 배포하므로, `package.json` 이 그 버전을 선언하고 있는 동안에는 **버전을 바꾸지 않는 문서 PR 머지만으로도 재배포된다.**

실측: `2.0.0` 을 지운 뒤 문서 PR 을 머지했더니 _"our local version (2.0.0) has not been published on npm"_ 으로 다시 배포됐다.

**순서**: 되돌리는 커밋을 먼저 머지해 `main` 이 그 버전을 더는 선언하지 않게 하고, **그다음** 레지스트리에서 지운다.

## 머지 순서가 버전 계약의 일부다

배포가 자동이므로 **`main` 의 현재 버전 위에서 범프가 계산된다.** 되돌리기가 대기 중일 때 등급 있는 changeset 을 먼저 넣으면 **되돌리려던 버전 위에서 범프한다** — 실측: `2.0.0` 상태에서 `patch` 를 넣으면 `2.0.1` 이 나간다.

등급 있는 changeset 을 가진 PR 이 여럿 열려 있으면 **머지 순서를 정하고 근거를 적어라.** 빈 changeset 끼리는 순서가 무관하다.

## changeset 본문에 적을 것

- **무엇이 깨지는가** — 추상적으로 쓰지 말고 소비처가 만날 증상으로
- **대체 경로** — 제거만 적으면 소비처가 갈 곳을 모른다. 경로는 실재를 확인하고 적어라
- **누가 영향받는가** — 알려진 소비처의 버전 범위를 확인해서. 「아무도 안 쓴다」는 확인한 범위까지만 참이다

**changeset 은 CHANGELOG 로 굳어 되돌릴 수 없다.** PR 본문보다 오래 읽히므로 머지 전에 사실을 확인한다.
