# 스토리 결정성 (Story Determinism)

Chromatic 스냅샷은 **실행 시점의 렌더 결과**를 찍는다. 스토리가 렌더 중에 `new Date()` 를
호출하면 스냅샷이 매일 달라지고, Chromatic 은 매일 "변경" 을 낸다.

## 왜 이것이 검사를 무력화하는가

거짓 양성은 단지 시끄러운 것이 아니다. **매일 반복되면 사람이 맹목 수락을 학습한다.**
그 순간 시각 회귀 검사의 신호는 0이 된다 — 진짜 회귀가 섞여 들어와도 같이 수락된다.

실제로 이 저장소에서 그렇게 됐다. 한 PR 에서 21건이 맹목 수락됐고 다음 빌드에서 27건이 또 왔다.
그 변경들은 **코드 때문이 아니라 날짜 때문**이었다 — 해당 PR 의 DOM 대조에서 "코드로 설명되는 것
0건" 이 이미 나와 있었는데도 원인이 날짜라는 것은 나중에야 밝혀졌다.

## 규칙

**스토리는 렌더 중에 비결정적 값을 만들지 않는다.**
`new Date()` · `Date.now()` · `Math.random()` · `performance.now()` · `crypto.randomUUID()`.

```tsx
// ❌ 렌더 중 — 스냅샷이 매일 달라진다
const [date, setDate] = React.useState<Date | undefined>(new Date())

// ✅ 고정 값
const fixedToday = () => new Date(2026, 0, 15)
const [date, setDate] = React.useState<Date | undefined>(fixedToday())
```

**이벤트 핸들러 안은 괜찮다.** 스냅샷은 렌더 결과만 찍으므로 클릭해야 실행되는 코드는 영향이 없다.
그리고 그것이 데모의 의미인 경우도 있다 — "이번 달" 버튼이 현재 달을 계산하는 것을 고정하면
버튼이 거짓말을 하게 된다.

```tsx
// ✅ 클릭해야 실행된다 — 스냅샷 무관
const setThisMonth = () => {
  const now = new Date()
  setRange({ start: startOfMonth(now), end: endOfMonth(now) })
}
```

## 고정 날짜는 반드시 과거로 잡는다

시간은 앞으로만 간다. 과거 달로 잡으면 `isToday` 가 다시 매칭될 일이 없어 **영구히 안정**이다.
미래 날짜로 잡으면 그 날이 왔을 때 다시 깨진다.

## 달만 고정하고 선택은 건드리지 않기 — `defaultFocusedDate`

`defaultDate`(단일) · `defaultRange`(범위)는 값을 **선택**한다. "기본 상태" 를 보여주는 스토리에
쓰면 있지도 않던 선택 표시가 생겨 데모의 의미가 바뀐다.

보이는 달만 고정하려면 `defaultFocusedDate` 를 쓴다 (react-aria `defaultFocusedValue`).

```tsx
const cal = useCalendar({ defaultFocusedDate: fixedToday(), locale: 'ko-KR' })
```

`useCalendar` · `useRangeCalendar` · `DatePicker` · `RangeDatePicker` 가 모두 받는다.

**우선순위(실측)**: `value`/`defaultDate` 와 함께 주면 **표시 월은 `defaultFocusedDate` 가 이긴다.**
선택 값 자체는 바뀌지 않지만, 둘이 서로 다른 달을 가리키면 선택된 날짜가 첫 렌더에서 보이지 않는다.

## 날짜를 고정하면 스토리만으로는 부족하다

`isToday` 는 스토리 코드가 아니라 **훅**이 계산한다
(`use-calendar.ts` · `use-range-calendar.ts` 가 `today(getLocalTimeZone())` 과 비교하고,
`Calendar.Day` 가 그 결과로 today 인디케이터를 자동 렌더한다).

따라서 스토리에서 `new Date()` 를 전부 없애도, **보이는 달에 실제 오늘이 들어 있으면**
인디케이터가 매일 다른 셀로 옮겨 다닌다. 달 자체를 고정해야 한다.

## 기계 검사

`src/lib/__test__/story-determinism.test.ts` 가 `src/**/*.stories.tsx` 전체를 AST 로 훑어
**렌더 경로에서 평가되는** 비결정 호출을 찾는다.

판정은 **fail-closed** 다: 감싸는 함수 중 하나라도 이벤트 핸들러에 바인딩되어 있으면 지연 실행으로
보고, 그렇지 않으면 전부 렌더 경로로 본다. 판정할 수 없으면 위반으로 올린다 — 오탐은 시끄럽지만
누락은 조용히 거짓 양성을 되돌린다.

처음에는 **함수 중첩 깊이**로 판정했다가 세 번 샜다. 깊이는 "언제 실행되는가" 의 대리 지표일
뿐이어서, 실제로 렌더 중에 실행되는 것들을 콜백으로 오분류했다:

| 형태                            | 왜 샜나                                         |
| ------------------------------- | ----------------------------------------------- |
| `(() => Date.now())()`          | IIFE 는 즉시 실행되는데 함수 한 겹으로 세어졌다 |
| `useState(() => new Date())`    | 지연 초기화는 첫 렌더에 실행된다                |
| `useMemo(() => new Date(), [])` | 메모 팩토리도 렌더 중에 실행된다                |

예외를 하나씩 열거하는 방식으로는 네 번째가 또 나온다. **실제로 나왔다** — 판정을 직접 방식으로
바꾼 뒤에도 같은 계열의 네 번째가 남아 있었다:

| 형태                                                               | 왜 샜나                                           |
| ------------------------------------------------------------------ | ------------------------------------------------- |
| `const f = () => Date.now()`<br>`<div data-x={f()} onClick={f} />` | 핸들러 참조가 **하나라도** 있으면 통째로 면제했다 |

질문이 한쪽만 향해 있었다 — "핸들러에 쓰이는가" 를 물으면 렌더에서도 쓰는 함수가 빠져나간다.
**"핸들러에만 쓰이는가"** 로 양방향으로 바꿨다. 렌더 경로 참조가 하나라도 있으면 면제하지 않는다. 그래서 대리 지표를 버리고
"이벤트 핸들러에 바인딩되었는가" 라는 **직접 판정**으로 바꿨다.

핸들러 판정도 형태를 열거하지 않는다. 함수가 묶이는 **이름**을 찾고(변수·함수 선언·객체 속성),
그 이름의 참조가 **전부** `on[A-Z]` JSX 속성 안에만 있는지 본다. 그래서 아래가 한 규칙이다:

```tsx
onClick={() => …}                                   // 직접
const h = () => …;                    onClick={h}   // 변수
function h() {}                       onClick={h}   // 함수 선언
const h = useCallback(() => …, [])    onClick={h}   // 한 겹 감싼 것
const o = { onClick: () => … }        onClick={o.onClick}  // 객체 속성
const o = { onClick() { … } }         onClick={o.onClick}  // 축약 메서드
```

반대로 아래는 면제되지 않는다 — 렌더 중에도 실행되기 때문이다:

```tsx
const stamp = () => Date.now()
<div data-stamp={String(stamp())} onClick={stamp} />   // ❌ 위반으로 잡힌다
```

### 검출 대상

`new Date()`(인자 없음 또는 spread) · **`Date()`(new 없이 — 현재 시각 문자열을 돌려준다)** ·
`Date.now()` · `Math.random()` · `performance.now()` · `crypto.randomUUID()`.
`Date['now']()` 처럼 표기법만 바꾼 것도 같이 본다.

> **`Date()` 만 조건부다.** 파일이 `Date` 라는 이름을 **값으로** 선언·import 하면
> (`const Date = …` · `import { Date } from './date-util'` · `function`/`class Date`)
> 전역 `Date` 가 아니라고 보고 비켜간다. 타입 전용 import(`import type { Date }`)는 값
> 바인딩을 만들지 않으므로 **섀도잉이 아니다** — 여전히 잡는다.

### 이 가드가 **잡지 못하는 것** (실측)

판정은 **이름 기반**이다. 이름을 지우면 뚫린다:

| 우회                                                                              | 결과      |
| --------------------------------------------------------------------------------- | --------- |
| `const D = Date; new D()`                                                         | 못 잡는다 |
| `const { now } = Date; now()`                                                     | 못 잡는다 |
| 파일이 `Date` 를 **값으로** 선언·import 한 뒤 그 파일에서 진짜 전역 `Date()` 호출 | 못 잡는다 |

셋째 줄은 **이름을 지우지 않아도 뚫리는** 경로다 — 위 두 줄과 원인이 다르다. 섀도잉 오탐을
없애려고 넣은 면제가 스코프를 보지 않아서, 파일 어느 구석에서든 `Date` 를 가리면 그 파일의
진짜 전역 `Date()` 까지 함께 면제된다. **이 가드에서 유일하게 fail-open 인 지점이다.**
그럼에도 이쪽을 택한 이유는 `Date()`(new 없는 호출) 자체가 드물고, 그 이름을 가리는 스토리가
저장소에 0건이며, 오탐이 나면 정상 코드가 막혀 사람이 가드를 꺼버리기 때문이다.

이름을 지운 우회를 잡으려면 `ts.TypeChecker` 로 심볼을 따라가야 하고, 그러려면 프로그램 전체를
로드해야 해서 이 가드의 비용 특성이 달라진다. 또한 이름 매칭은 **스코프를 보지 않는다** —
같은 이름이 파일의 다른 스코프에도 있으면 그쪽 참조가 이쪽 판정에 섞인다. 다만 판정을
"핸들러에만 쓰이는가" 로 바꾼 뒤로는 섞이는 방향이 **더 많이 잡는 쪽**이라 fail-closed 를 깨지 않는다.

**이 한계는 감추지 않고 픽스처 테스트로 고정해 두었다** (`story-determinism.test.ts` 의
"알려진 한계" 케이스). 가드가 "전부 잡는다" 고 믿는 것이 가드가 없는 것보다 위험하기 때문이다.

### 이 가드가 **잘못 잡는 것** (실측, 전부 픽스처로 고정)

문서의 "감추지 않는다" 원칙은 누락뿐 아니라 **오탐**에도 적용된다. 가드가 멀쩡한 코드를 막으면
사람이 가드를 끄고, 꺼진 가드는 없는 것과 같다. 지금 남아 있는 오탐:

| 오탐                                                                   | 왜 남기나                                                 |
| ---------------------------------------------------------------------- | --------------------------------------------------------- |
| class 메서드를 핸들러로 (`onClick={c.onClick}`)                        | 메서드→인스턴스 변수는 심볼 해석 필요. 스토리에 class 0건 |
| 핸들러 변수를 객체에 담아 `h.onClick` 로 전달                          | 멤버 이름이 참조 계수에서 빠져 `handlerRefs=0` 이 된다    |
| `useCallback(() => helper(), [])` 안에서 부르는 도우미                 | "핸들러 안에서만 불리는가" 를 **전이적으로** 따라가야 함  |
| `Date` 를 섀도잉한 파일의 `new Date()` · `Date.now()`                  | 섀도잉 면제를 `Date()` 에만 걸었다 (아래)                 |
| 파라미터·구조분해로 만든 `Date` (`(Date) => …` · `const { Date } = …`) | 인정하면 유일한 fail-open 지점이 넓어진다                 |

마지막 줄은 **의도적인 기각**이다(CodeRabbit 이 고치라고 지적했다). 파라미터·구조분해도
값 바인딩이니 인정하는 것이 "정확" 하지만, **방향이 반대다** — 섀도잉 면제는 이 가드에서
유일한 fail-open 지점이고, 인정하는 선언 형태를 늘리면 그 구멍이 그만큼 넓어진다.
두 실패 모두 저장소 실사례 0건이므로, 확률이 같다면 **시끄러운 쪽**을 남긴다.

그 앞줄은 **구현 범위가 논거 범위보다 좁다**는 뜻이다. "가드가 멀쩡한 코드를 막으면 안 된다"
는 논거를 대면서 정작 그 파일에서 훨씬 흔한 `new Date()` 는 그대로 막는다. 의도적이다 —
`new Date()` 는 사전 확률이 압도적으로 높아 섀도잉을 이유로 면제하면 진짜 결함을 놓칠 위험이
`Date()` 와 비교가 안 된다. 다만 비대칭이라는 사실은 적어 둔다.

검사기는 위반 수와 함께 **`filesScanned`(검사 대상으로 인식한 파일 수)** 를 반환한다.
테스트는 그것을 단정하고 **출력에도 남긴다**(`[story-determinism] 검사 대상 … = 64개`).
"위반 0건" 이 *깨끗해서*인지 *아무것도 안 봐서*인지 구분하기 위한 것이다 — 이 저장소에서
반복해 밟은 함정이다. 스캔 기준 경로는 `process.cwd()` 가 아니라 테스트 파일 위치에서 잡는다.
실행 위치에 따라 대상이 달라지면 "0건" 이 "엉뚱한 데를 봤다" 가 될 수 있다.

**검사 범위는 Storybook 이 읽는 뿌리 전부다.** `src/**` 만 보면 `tokens/stories/**` 5개는
Chromatic 이 스냅샷하는데 가드는 보지 않는다 — 지금 그 5개에 비결정 호출이 없더라도,
**검사 범위가 스냅샷 범위보다 좁다는 사실 자체가 구멍**이다. 확장자도 Storybook 과 맞춘다
(`.stories.{tsx,ts,jsx,js,mjs}`). 현재 검사 대상 69개.

**하한(`> 30`)으로 단정하지 않는다.** 하한은 "일부를 조용히 버림" 을 못 잡는다 — 64개 중 33개가
사라져도 통과한다. 실제로 수집기가 `compositions/` 를 건너뛰게 만들자 40개만 스캔하면서
트리에 위반이 있는데도 전부 통과했다. 그래서 (1) 독립적으로 센 **파일 목록과 등식**으로 비교하고,
(2) 날짜 계열 스토리 5개가 **이름으로** 스캔 목록에 있는지 따로 단정한다. (1)만으로는 다른 파일이
늘어 수가 맞는 경우를 놓치고, 실제로 지켜야 하는 것은 (2) 다.

## 알려진 커버리지 구멍

**today 인디케이터가 올바른 셀에 붙는지는 시각 회귀로 덮이지 않는다.**

모든 캘린더 스토리를 과거 달로 고정했으므로 `isToday` 가 어떤 스토리에서도 매칭되지 않는다.
이 구멍을 둘로 나눠 메웠다:

| 무엇                         | 어디서                                         | 왜 거기서                                       |
| ---------------------------- | ---------------------------------------------- | ----------------------------------------------- |
| 인디케이터의 **모양**        | `TodayIndicatorAppearance` 스토리 (Chromatic)  | 요소를 직접 렌더하므로 날짜와 무관하다          |
| 올바른 셀에 붙는지(**배치**) | `calendar-today.test.tsx` (`vi.setSystemTime`) | 실행 날짜에 의존하므로 시각 회귀로 다룰 수 없다 |

즉 **"실제 캘린더 안에서 인디케이터가 놓인 모습"** 은 여전히 시각적으로 확인되지 않는다.
스타일이 깨져도 배치 테스트는 통과한다. 이것을 닫으려면 `today` 를 주입 가능하게 만들어야 하는데
(훅 옵션 → 컨텍스트 → `Calendar.Day` → `useCalendarCell` 로 4계층을 관통해야 한다) 공개 API
설계 결정이라 이 작업의 범위 밖으로 두었다.
