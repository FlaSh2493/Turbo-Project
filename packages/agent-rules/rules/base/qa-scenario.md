# QA 시나리오

흐름이 끝까지 동작하는지는 렌더 테스트가 확인하고, 렌더 테스트가 보지 못하는 것만 사람이 본다. 언제 어디에 쓰는지는 `[BASE-REQ]`를 따른다. 이 파일은 쓰는 법만 다룬다.

## [QA-FORM] 양식

플랜에는 아래처럼 쓴다.

```markdown
## QA 시나리오

- 대상: <로컬 | URL>
- 계정/역할: <어떤 계정으로 보는지>

### 흐름

1. <사용자가 하는 일>

### 렌더 테스트로 확인할 것

- <흐름 번호>: <화면에서 바뀌는 결과>

### 직접 확인할 것

- <렌더 테스트가 보지 못하는 것> (<화면>, <화면 폭>)
```

PR 본문에는 PR 템플릿의 두 표로 옮긴다. "렌더 테스트로 확인할 것"은 `## 렌더 테스트로 확인한 흐름`에 흐름과 테스트 파일을, "직접 확인할 것"은 `## 직접 확인할 것`에 화면과 확인할 것을 적는다. 대상과 계정은 `## 직접 확인할 것` 첫 줄에 쓴다. 결과 칸은 두지 않는다.

## [QA-WRITE] 쓰는 법

- 흐름은 사용자가 하는 일로 쓴다. 셀렉터, 클래스명, 버튼 위치는 쓰지 않는다.
- 수락 기준은 요구사항 출처에서 가져오고, 화면에서 판정할 수 있는 문장으로 쓴다.
- 권한·빈 값·실패 응답처럼 분기가 있으면 분기마다 흐름을 나눈다.
- 이번 변경이 아니어도 바뀐 코드를 쓰는 화면과 이동 경로는 기존 기능 흐름으로 따로 적는다.
- 렌더 테스트로 확인할 것: 클릭·입력 뒤 바뀌는 문구, 상태, 보이고 숨는 요소, 버튼이 켜지고 꺼지는 것, 실패 응답 때 보이는 안내처럼 DOM으로 판정할 수 있는 결과.
- 직접 확인할 것: 레이아웃, 겹침, 잘림, 말줄임, 색과 대비, 화면 폭에 따른 배치처럼 jsdom이 그리지 않아 렌더 테스트로 확인할 수 없는 것만 적는다. 렌더 테스트로 확인할 수 있는 것을 사람에게 넘기지 않는다.
