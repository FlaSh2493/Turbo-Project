## [BASE-REQ] 요구사항

- 변경은 Jira 이슈에서 시작한다. 이슈의 Problem·Requirements·Acceptance Criteria·Constraints·Out of Scope가 이번 변경의 범위다. 비어 있는 항목은 구현 전에 사용자에게 묻는다.
- 이슈가 없으면 사용자 요청을 출처로 삼는다. 위 항목을 플랜에 정리하고 구현 전에 사용자 확인을 받는다. 플랜을 쓰지 않는 작업이면 대화로 확인받고 PR 본문에 쓴다.
- 수락 기준과 검증 시나리오는 `## 이 레포`의 요구사항 출처에서 만든다. 출처에 없는 요구사항을 만들지 않는다.
- 화면, 이동, 인터랙션, 권한별 분기가 바뀌는 작업이면 `## QA 시나리오`를 쓴다. 내부 리팩터, API·타입 변경, 문서 변경에는 쓰지 않는다.
- QA 시나리오는 플랜에 쓰고 PR 본문에 옮긴다. 플랜을 쓰지 않는 작업이면 대화에서 정리해 확인받고 draft PR 본문에 쓴다. `[BASE-WORK]` 2단계에서 찾은 화면과 이동 경로를 기존 기능 흐름으로 넣는다. 렌더 테스트로 확인할 것과 직접 확인할 것을 나눠 쓴다. 양식은 [common/qa-scenario.md](.agents/rules/common/qa-scenario.md).

## [BASE-WORK] 작업 순서

에이전트가 작업 중에 한다. 사람은 요청을 주고, 화면과 에이전트가 확인하지 못했다고 보고한 부분을 직접 확인한다.

1. 작업을 시작하면 Claude Code 워크트리(`.claude/worktrees/<이름>/`)를 만들고 그 안에서 작업한다. 브랜치 이름은 `## 브랜치와 배포`를 따르고, 다르게 만들어졌으면 플랜을 쓰기 전에 `git branch -m`으로 바꾼다. 워크트리에서도 `## 이 레포`의 설치 명령을 먼저 돌린다.
2. 구현 전에 수락 기준을 정리한다. 출처는 `[BASE-REQ]`를 따른다. 바뀔 코드를 쓰는 화면과 이동 경로를 코드에서 찾는다. 그다음 플랜을 쓸지 정한다. 기본은 쓴다. 쓰는 법은 [common/plan.md](.agents/rules/common/plan.md)를 따른다.
   - 반드시 쓴다: 화면 이동·진입 경로·사용자 단계가 바뀐다, `## 이 레포`의 큰 변경으로 보는 영역을 건드린다, API 계약이나 저장되는 데이터 형식이 바뀐다, 구현 방법을 정하지 못했다. 이때는 플랜을 승인받은 뒤 구현한다.
   - 위에 해당하지 않고 아래 중 하나면 플랜 대신 PR 본문에 영향받는 곳을 쓴다: 의존성·CI·설정만 바꾼다, 문구·스타일만 바꾼다, 동작이 바뀌지 않는 리팩터다, 한 화면 안에서 끝나는 버그 수정이다, 문서만 바꾼다.
3. 동작이 바뀌면 실패하는 테스트를 먼저 쓴다. 빈 값, 경계값, 실패 응답, 권한 없음, 중복·동시 요청을 검토하고 해당하는 것은 테스트로 남긴다.
4. `## 명령`의 검증 명령을 돌린다. 실패는 원인을 고친다(`[BASE-NO-BYPASS]`).
5. 동작을 확인하고 증거를 남긴다. 외부 연동과 API는 에이전트가 실행한 요청과 응답이다. 화면의 흐름은 QA 시나리오의 "렌더 테스트로 확인할 것"을 렌더 테스트로 만들어 확인한다. 렌더 테스트가 보지 못하는 것(레이아웃, 겹침, 잘림, 색)은 "직접 확인할 것"으로 사용자에게 알리고, `## 명령`의 확인할 화면 폭에서 사용자가 직접 본다. 확인하지 못한 부분은 확인 안 함으로 적는다.
6. ready 전에 실제 diff로 바뀐 코드를 쓰는 화면과 이동 경로를 다시 찾고, 영향받는 곳과 QA 시나리오의 기존 기능 흐름을 맞춘다. 플랜이 있으면 플랜을 고치고, 플랜을 쓰지 않는 작업이면 PR 본문에 쓸 초안을 고친다.
7. PR은 draft로 연다.
8. PR 본문은 PR 템플릿 순서대로 요약, 주의할 점, 직접 확인할 것, 영향받는 곳, 수락 기준과 테스트 파일, 렌더 테스트로 확인한 흐름, 되돌리는 방법을 쓴다. 수락 기준 표에는 케이스 번호 대신 테스트 파일을 적는다. 주의할 점에는 작업하면서 겪은 로컬 문제를 적지 않는다. 플랜이 있으면 플랜에서 옮긴다. 플랜이 원본이고 PR 본문은 결과물이라, 작업 중 기준이 바뀌면 PR 본문을 직접 고치지 말고 플랜을 먼저 고친 뒤 다시 옮긴다. 플랜을 쓰지 않는 작업이면 PR 본문에 직접 쓴다.
9. 위 검사와 확인, 본문 작성을 마친 뒤 ready로 바꾼다. CodeRabbit은 ready PR만 리뷰하고 리뷰 횟수에 한도가 있다. ready 상태에서 커밋을 쌓으면 한도를 쓴다.
10. CodeRabbit 지적은 코드로 확인해서 고친다. 같은 종류는 전부 고치고, 반영하지 않을 지적에는 이유를 답글로 남긴다.
11. 수동으로 재현한 문제는 테스트로 바꿔 다시 나오지 않게 한다.
12. PR이 머지되면 플랜 파일, 워크트리, 로컬 브랜치를 지운다.

## 🔒 [BASE-NO-BYPASS] 검사를 건너뛰거나 덮지 않는다

- `--no-verify`로 훅을 건너뛰지 않는다.
- 실패를 `any`·`@ts-ignore`·`eslint-disable`·테스트 skip으로 덮지 않는다. 고칠 수 없는 경우의 예외는 [common/comments.md](.agents/rules/common/comments.md)의 `[COMMENT-DIRECTIVE]`를 따른다.

## [BASE-VERIFY] 검증 원칙

- 완료 기준은 `## 명령`의 검증 명령이다. CI와 같은 검사를 로컬에서 먼저 돌린다. `## 명령`의 PR에서만 도는 검사를 로컬에서 돌리지 않았으면 결과 보고에 적는다.
- `## 명령`에 CI에서 돌지 않는다고 적힌 검사(정적 분석 등)는 push 전에 로컬에서 돌린다. 고치지 않고 남기는 경고는 PR 본문에 `파일:라인 | 규칙 | 이유`로 남긴다.
- UI를 바꿨다면 검증 명령으로 끝나지 않는다. jsdom과 빌드는 레이아웃·스타일 cascade·인터랙션을 보지 못하고, HTTP 200은 증거가 아니다. 화면 확인은 `[BASE-WORK]` 5단계를 따른다.

## [BASE-COMMIT] 커밋과 PR

- 커밋 제목은 `type(scope): 한글 제목 (ABC-1234)`이다. type은 `build`·`chore`·`ci`·`docs`·`feat`·`fix`·`perf`·`refactor`·`revert`·`style`·`test`. scope는 `## 브랜치와 배포`의 기준을 따른다. 티켓 키는 브랜치 이름에서 가져오고 없으면 생략한다. 제목은 100자 이하, 마침표 없이 쓴다.
- 본문에는 무엇을 왜 바꿨는지 쓴다.
- 보호 브랜치에 바로 커밋하지 않는다. 보호 브랜치를 출처로 PR을 여는 것은 승격·백포트뿐이다. 보호 브랜치와 base는 `## 브랜치와 배포`를 따른다.
- PR 제목은 커밋 제목과 같은 형식이다. 본문은 PR 템플릿(`.github/pull_request_template.md`)이 있으면 그 섹션을 채운다. PR을 열기 전에 `git log origin/<base>..HEAD`로 무관한 커밋이 섞이지 않았는지 본다.
- PR 본문은 리뷰어가 읽는 글이다. 영어를 옮긴 듯한 말 대신 평소에 쓰는 말로 쓴다("URL을 해제한다" 대신 "메모리를 풀어 준다", "말줄임된다" 대신 "한 줄로 잘린다").
- 작업과 Git 조작은 이 작업의 워크트리 안에서 하고, 관련 없는 사용자 변경을 보존한다.

## [BASE-DEPLOY] 배포와 장애 대응

- 머지가 곧 배포다. 어느 브랜치가 어디에 배포되는지는 `## 브랜치와 배포`에 있다.
- 되돌리기는 revert PR이다.
- 장애가 나면 고치기 전에 먼저 되돌리고, 공유한 뒤 원인을 찾는다. 되돌리면 이미 저장된 데이터의 형식이나 다른 서비스와 맞춘 계약이 깨지는 변경이면, 되돌리기 전에 사람에게 묻는다.

## 🔒 [BASE-CONFIRM] 실행 전 확인이 필요한 작업

아래는 사용자 확인 없이 하지 않는다. 일반적인 코드 수정은 괜찮지만, 아래에 적힌 변경은 코드 변경이어도 확인이 필요하다. `## 이 레포`의 "확인받을 작업"에 적힌 작업도 같다.

- **PR 머지와 보호 브랜치 푸시.** 머지가 곧 배포다.
- 커밋과 PR 생성. 사용자가 요청했을 때만 한다.
- 외부 도구에 diff 보내기. 보내기 전에 보낼 내용 전체(바뀐 줄 주변의 맥락 포함)에서 secret을 찾고, 있으면 보내지 않는다. `.env*`는 보내지 않는다.

## 🔒 [BASE-GENERATED] 공통 규칙과 레포 규칙

- `AGENTS.md`의 agent-rules 블록과 `.agents/rules/common/`은 `@turbo-project/agent-rules`가 쓴다. 직접 고치지 않는다. 버전을 올리면 `pnpm exec agent-rules init`으로 다시 쓰고 `pnpm agents:check`로 확인한다.
- 블록 밖의 `AGENTS.md`와 `.agents/rules/custom/`은 레포가 관리한다. 다른 패키지가 쓰는 블록(`<!-- BEGIN:<이름> -->`~`<!-- END:<이름> -->`)도 직접 고치지 않는다.
- 공통 규칙을 이 레포만 다르게 하거나 끄려면 `AGENTS.md`의 `## 예외`에 쓴다(`[RULEFILE-EXCEPTION]`). 🔒 규칙은 바꾸거나 끄지 않는다.
- 모든 레포에 맞는 규칙을 바꾸거나 더하려면 turbo-project의 `packages/agent-rules`를 고친다. 레포는 새 버전을 설치하면 반영된다.
