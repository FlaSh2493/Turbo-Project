# 문서

| 문서      | 위치                   | 담는 것                                | 수명                        |
| --------- | ---------------------- | -------------------------------------- | --------------------------- |
| 변경 요청 | Jira 이슈              | 이번에 무엇을 바꾸는가                 | 변경 하나                   |
| 스펙      | `docs/specs/<도메인>/` | 지금 시스템이 보장하는 동작            | 계속 갱신한다               |
| 플랜      | `docs/plans/`          | 이번 변경의 설계·구현 계획·QA 시나리오 | 작업이 끝나면 고치지 않는다 |

## [DOC-SPEC] 스펙

- 현재 상태만 쓴다. 이전 동작, 티켓 키, 변경 이력은 쓰지 않는다.
- 현재 동작은 스펙으로 판단한다. 지난 플랜을 모아 추론하지 않는다.
- 동작은 `Given / When / Then` 시나리오로 쓴다.
- 기능 스펙(`<도메인>/<기능>.md`)은 기능 하나의 동작을 쓴다. 흐름 스펙(`<도메인>/flows.md`)은 처음부터 끝까지의 사용자 경로를 쓰고 관련 기능 스펙을 링크한다.
- 테스트와 동작 확인을 통과한 동작만 쓴다.

## [DOC-PLAN] 플랜

- 설계 판단이 남은 변경에만 쓴다. 작은 수정은 PR 본문에 영향 분석을 쓴다.
- 파일 이름은 `<티켓 키>-<slug>.md`, 티켓이 없으면 `<date>-<slug>.md`다.
- 출처, 현재 상태, 영향 분석(영향받는 기능·흐름 스펙), 구현 단계, 검증 순서로 쓴다. 결정이 남은 큰 변경은 승인받은 뒤 구현한다.

## [DOC-UPDATE] 스펙 갱신

- 동작이 바뀐 작업은 같은 PR에서 ready 전에 관련 스펙을 갱신한다.
- 바뀐 기능의 스펙이 없으면 코드와 테스트를 읽고 현재 동작으로 새로 만든다.
